# 证据自审与功能验收

## 原则与职责

- 流程：核对需求 → 必要澄清 → 执行一个功能 → 自审与验证 → 用户验收 → 下一功能。
- 一个可独立验证、结果可观察的功能为一个单元，不按文件或工具调用拆分。用户确认前，不开始或后台实现下一单元；当前单元内的实现、修复、复测无需分别验收。
- 结论必须有证据；不承诺绝对无 bug，不擅定业务规则或扩展范围，额外功能只作建议。
- 遵守用户指令、AGENTS.md、核心文档及环境审批；Skill 不扩大授权，也不保证全局自动加载。
- 职责分开：全局指令保留自审、证据、红线和单问原则；Skill 管执行与验收；核心文档管需求和决定；项目状态文件管进度。项目事实不写入通用 Skill，不自动修改全局指令。
- 小改动简化检查与报告，但不跳过功能验收。

## 1. 核对与澄清

1. 定向读取指定的需求、提示词、核心文档及项目规则；确认目标、授权、阶段、现有改动和验证结果，复用已有证据。
2. 当前功能明确目标、范围、需求依据、实现与缺口、通过标准和验收方式。依赖不具备时先拆分可验证的基础功能。
3. 文档管需求，代码与运行结果证明实现；不一致时记录差异，不改写需求掩盖问题。仅在文档维护已授权时更新，否则提建议。
4. 材料无法访问时说明缺失与影响，不用项目名称、记忆或旧日志编造现状。影响执行的文档冲突指出位置并询问。

先查材料再问；问题数量按需要决定，每次只问一个简练关键问题，说明影响，收到答案后再判断下一问：

- 业务、权限、范围、验收及影响体验、成本、数据边界或架构承诺的取舍不明确时，问用户。
- 代码行为、兼容性、错误原因先用只读调查或已授权测试确认；仍不明确且影响执行时再问。
- 常规实现细节在既定范围内处理；需求与授权明确时直接执行，不增设批准环节。
- 功能边界或通过标准不明时先问；阻塞期间只做不依赖答案的工作。

## 2. 执行边界

授权范围内可分析、创建文件、改代码、联网和测试；改动最小且充分，保留已有工作。无关问题仅登记，不顺手修复或重构。联网遵守适用规则，不上传私有内容或凭据。

以下动作必须先获用户明确批准：

- 删除文件、目录或 Git 历史。
- 修改 .env、密钥、token、证书或 CI/CD 配置。
- git push、git rebase、git reset --hard、强制推送。
- 公开发布、生产部署及项目文档规定的其他红线动作。

不自动 commit 或 push；明确要求提交时先展示变更摘要，提交信息用简洁英文。测试授权不包含安装环境、数据库写入或外部写入；涉及这些动作先核对授权，未授权则询问。

## 3. 主动自审

执行前、关键新证据出现时、功能完成后自审。仅报告结论、依据、影响和待决定问题，不展示完整思考过程或重复问卷。

| 自问 | 使用方式 |
| --- | --- |
| 最没把握的是什么？ | 找关键未验证假设，用代码或测试核实 |
| 最大遗漏是什么？ | 对照需求检查正常、错误、边界、权限、数据和依赖 |
| 三个月后为何失效？ | 按相关性检查规模、依赖和数据变化、维护成本；未验证的标为风险假设，不当作 bug |
| 最值得新增什么领先功能？ | 仅在规划、头脑风暴或用户要求建议时使用；说明收益、代价和依据，无可靠行业资料不称行业领先 |
| 怎样提高对话效率？ | 合并重复检查，减少无效提问，保留核心决定和验收证据 |

问题记录：需求位置、代码位置、复现或来源、影响、最小修复。范围内且业务明确的可修复并复测；新业务选择、红线或扩展范围先问。

## 4. 分级验证与收敛

按实际影响最高项分级，不按改动量判断；只执行相关检查：

| 风险 | 情况 | 检查 |
| --- | --- | --- |
| 低 | 文案、样式、无逻辑变化的展示 | 改动、实际展示及受影响行为，不强制新增自动化测试 |
| 中 | 查询、转换、业务规则、接口 | 需求通过标准，正常、错误与边界输入，实际接口或运行结果 |
| 高 | 权限、数据写入、资金、敏感数据、不可逆操作 | 中风险检查加适用的越权、完整性、精度、重复执行和恢复验证 |

- 实现后从需求重新推导检查项，不仅照抄实现逻辑；适用时用明确预期、独立计算或可信数据对照，避免实现与测试共享错误假设。
- 默认不使用子代理；不同证据与方法不等于独立审计。
- 只用实际结果证明对应行为；编译、导入或模拟测试不证明业务、真实外部服务可用。缺少运行条件时标明未验证。
- 修复后重跑受影响检查，不无故重跑全部检查。
- 条件未变、无新证据且只重复同一失败操作时停止；有新证据或可检验假设可继续定向排查，不按固定次数中断。需用户协助时报告阻塞并问一个关键问题。
- 通过标准满足、重要风险已说明且无新的相关证据时结束自审。影响验收的失败或关键未验证项存在时，不称完成，先报告阻塞或处理问题。

## 5. 零基础验收

每个功能给出可实际检查的入口、操作与预期结果。专业名词首次出现时附一句通俗解释；提供可点击代码位置，展示“需求 → 实现 → 证据”，不贴长代码或日志。

- 界面功能用实际产品页面；后台或数据功能优先复用页面、接口演示工具，也可用可检查的结果文件或输入输出对照。
- 展示实际输出、状态与适用的失败提示，区分真实结果和演示数据。现有方式不足或用户明确需要页面时，才建接入当前功能的最小验收页面，不建设额外平台。
- 新增服务、依赖、架构改变或越过文档边界时先问。页面无法运行时说明原因与未验证范围，不凭截图宣称通过。
- 不展示真实凭据或未授权敏感数据。用户验收确认业务与体验，技术验证确认正确性与风险；二者不互相替代，页面或用户确认不单独证明安全性、泛用性或无 bug。

报告默认简短，省略空项：

```text
当前功能：[名称；已验证/未验证/被阻塞]
结果：[用户能做什么]
依据：[需求、代码位置及验证摘要]
验收：[入口；操作 → 预期结果]
剩余问题：[影响、依据或未验证范围]
```

证据多时用表：业务要求 | 实现位置 | 技术验证 | 用户验收。日志按需读取，不重复历史与全部自问。

具备验收条件后只问：“这个功能是否验收通过，允许进入下一功能？”
明确确认才继续；“收到”、沉默、时间经过或测试通过均不算确认。用户报告问题时修复当前功能、复测并重新提交验收；验证受阻时如实说明，不误导用户确认。

## 6. 状态与复验

保留最小摘要：目标、权威文档、已确认决定、当前功能、改动、验证证据、未解决问题、用户验收。上下文压缩后先核对，不重做已完成工作或跳过验收。

每个功能保留一条记录，优先沿用编号，无编号则用短名称：

| 功能 | 需求依据与通过标准 | 实现位置 | 技术验证与证据 | 用户验收 | 未解决问题 |
| --- | --- | --- | --- | --- | --- |
| [编号/名称] | [文档位置、标准] | [文件、函数] | [通过/失败/未验证/被阻塞；证据] | [待确认/通过/未通过；确认依据] | [问题或无] |

仅状态变化时更新。已授权且有状态文件则定点维护；新建文件须有文档写入授权，否则用短消息保留，不每轮新建报告。
技术验证与用户验收分开记录，不能凭测试通过填写用户通过。已验收功能的需求或相关实现变化时，受影响部分标为待复验，做必要检查并重新验收；无关功能不重开。
